## 一、界面动画与分条渲染

**问题**：设置页、主界面每次按键都清屏重画，光标移动会闪；页面切换没有过渡。

**硬约束**：整屏 8 位缓冲要 32 KB，设备跑久后最大连续块只有约 31.7 KB（2026-11-07 E2E 实测），不能依赖整屏缓冲。

**底层方案（建议）：分条渲染**
- 从 arena 借一条 240×16 的 8 位条带（约 3.8 KB），所有重绘按区域在内存里画好再推屏。
- 页面绘制函数支持「在指定区域、按偏移画」，滑动动画 = 每帧按不同偏移推各条，不需要整屏缓冲。
- 借不到内存就不做动画，直接切换（与现在一致）。
- 设置页整页闪烁随这套机制一起解决（光标移动只重画两行）。

## 二、顶栏信息与信息页

- 数据来源：时间（NTP）；天气 / 温度（`place://weather`，缓存 30 分钟，需联网和高德 Key；**设备没有环境温度传感器**，芯片温度不是室温）；位置（GPS 需 Cap，逆地理编码需联网，缓存）；电量、Wi-Fi、LoRa 消息、下一个提醒、运行中的程序、剩余内存（本地）。
- 顶栏右侧约 150 像素，最多 2～3 项。方案 A 固定槽位；方案 B 一个轮播槽位（时间 → 天气 → 位置）+ Wi-Fi 常驻（倾向 B）。
- 信息页：一整页信息卡片，内容可配置；第三个标签页（Agent | SSH | 信息）或 Fn+I；复用 0.6 的面板（ui panel）定时刷新。

## 三、settings 扩展包

- Fn+W 设置页保持内置（离线、配置损坏时的兜底入口）。
- 新增 `settings://`：`read settings://` 返回设置页所有行（与菜单同一个函数）；`settings://font`；`settings://key/<provider>` 走设备掩码输入，Key 不经过大模型；`settings://webtoken/regenerate`、`settings://portal` 每次确认；`settings://statusbar`、`settings://infopage` 配置顶栏和信息页；`settings://animation`。
- WiFi / LoRa / SSH / 对话记忆不接管，指向已有的 `wifi://`、`lora://`、`device://local/context/length`。
- 对话记忆长度的保存收进 `settings_store::set_context_kb()`，设置页和 `local` 包共用。

## 四、画布表达式与状态（实时渲染程序）

> 已由 D7、D8 取代：不做画布专用脚本，改为扩展程序步骤 + 扩展包流式接口。下面保留为背景。

- 现状：`prog://` 无算术、无状态、`repeat` ≤ 10、以秒为单位；画布只有 `{t}` 线性变化和秒级 `source`。写不出「每帧读陀螺仪 → 算位置 → 重画」。
- 用户决定：**不加 ball 这类特殊指令**，做通用能力。
- 方案：画布增加 `vars`（状态）和 `update`（每帧赋值，只支持 `+ - * /`、比较、`min/max/abs`），参数里用 `"{x}"`；新增每帧读取的传感器绑定 `imu.ax / imu.ay`。
- 待定：表达式语法、变量个数上限、每帧赋值条数上限。

## 五、扩展包流式接口（D8 细化，2026-11-07 定）

**原则**：流是扩展包的第三种能力，跟一次性调用（`execute`）、离散事件（`triggers` / `watch`）并列。**URI 不区分是不是流**：同一个资源 `read` 一次、`stream` 订阅；能不能订阅由扩展包声明决定，不另设 `stream://` 前缀。

### 扩展包接口（registry.h 新增）

```cpp
struct StreamSpec {
    const char* target;       // "sensor://imu/acceleration"
    const char* fields;       // "x y z（g）"：字段名即程序里 a.x 的 x
    bool        input;        // false = 包产出（传感器）；true = 包接收（LED、音调）
    uint16_t    min_period;   // 最快多少毫秒一个新值
    const char* description;
};
struct StreamValue {          // 固定大小，不在堆上分配
    float   v[8];
    uint8_t count;
    char    text[16];
};
virtual void streams(std::vector<StreamSpec>& out) const {}
virtual bool open_stream(const String& target, String& error) { return false; }  // 第一个订阅者：开传感器
virtual void close_stream(const String& target) {}                                 // 最后一个离开：关掉
virtual bool sample(const String& target, StreamValue& out) { return false; }      // 取最新值
virtual bool feed(const String& target, const StreamValue& in) { return false; }   // 接收一个值
```

`sample` / `feed` 每秒约 30 次：**快、不阻塞、不分配内存**（写进《扩展包开发手册》）。

### 注册中心负责

- 订阅计数：第一个订阅调用 `open_stream`，最后一个退订调用 `close_stream`（传感器、麦克风只在用时开）。
- 同一帧对同一个流只取一次值（缓存）。
- 画布关闭、程序结束时自动退订。
- `discover(resources)` 列出流：`sensor://imu/acceleration  流 · 产出 · x y z（g）· 最快 10ms · 也可 read 读一次`。
- **保存程序 / 画布时校验**：目标必须是已声明的流；产出型不能 `send`；输入型不能当取值用；字段名必须在声明里。报错时给出可订阅的相近目标。

### 程序 / 画布里的写法

```json
{"stream": "sensor://imu/acceleration", "as": "a"}          // a.x a.y a.z
{"stream": "sensor://imu/acceleration?every=50ms", "as": "a"} // 可选频率，不快于声明的最快值
{"stream": "device://local/led", "send": "{r} {g} {b}"}     // 按声明的字段顺序，空格分隔
```

### 安全规则

- 产出型流只读，不需要确认。
- 输入型流只开放本机、可撤销的设备（LED、提示音、屏幕），每帧写不需要确认。
- 网络、红外、远端主机、文件**不开放成流**，仍走 `write` 并按原规则确认。

### 第一版的流（建议）

|:--|:--|:--|:--|:--|
| `sensor://imu/acceleration` | hardware | 产出 | x y z（g） | 最快 10ms |
| `sensor://imu/orientation` | hardware | 产出 | pitch roll（度） | 最快 10ms |

## 六、蓝牙（D10，2026-11-08 定）

**原则**：用 NimBLE 做 BLE，**把 BLE 作为通用能力完整暴露成 `ble` 扩展包**，让大肥鱼按需组合，不按场景写死功能。用到时才打开蓝牙，用完释放内存。ESP32-S3 只有 BLE，没有经典蓝牙。

| 能力 | 写法 | 说明 |
|:--|:--|:--|
| 扫描 | `read ble://scan` | 地址、名字、信号、广播数据（厂商数据、服务 UUID） |
| 查看设备 | `read ble://<地址>` | 连接并列出服务和特征（GATT） |
| 读写特征 | `read` / `write ble://<地址>/<服务>/<特征>` | 十六进制或文字；**写需要确认** |
| 订阅通知 | `{"stream": "ble://<地址>/<服务>/<特征>", "as": "h"}` | 特征通知作为流（D8） |
| 出现 / 消失 | 事件 `ble://seen/<地址>`、`ble://lost/<地址>` | 可触发程序 |
| 广播 / 当设备 | `write ble://advertise`、`ble://keyboard` | 广播数据；当 BLE 键盘（HID） |
| 配对 PIN | 设备掩码输入（`needs_secret`） | PIN 不经过大模型 |

**对 D8 的补充**：BLE 的流在运行时才知道，`streams()` 允许声明模式（`ble://<地址>/<服务>/<特征>`），包再提供 `is_stream(target)` 判断具体 URI 能否订阅；保存时校验调用它。

**步骤**：
1. 最小试验：NimBLE 扫描 + 连接读一个特征，实测 flash 增量、内存占用、开 BLE 时 Wi-Fi 与语音延迟的变化。
2. flash 只剩约 320 KB，可能需要改分区表（把不用的第二个应用分区并进应用分区）。这会挪动板载存储分区，升级时板载存储里的配置会丢（TF 卡不受影响），**拿到数字后由用户拍板**。
3. 实现完整的 `ble` 扩展包、E2E 用例（扫描、读写特征、订阅、事件）和《扩展包开发手册》里的说明。

### 最小试验结果（2026-11-08，NimBLE-Arduino 2.5.2，默认配置）

试验代码只在临时目录编译，未进仓库；试完已刷回正式 v0.6。

| 指标 | 正式固件 | 带 NimBLE 的试验固件 |
|:--|:--|:--|
| flash | 3,014,006 B（90%） | 3,216,470 B（96%），**+198 KB**，不改分区表也放得下 |
| 静态内存 | 71,756 B | 78,272 B，+6.4 KB |
| ready 时空闲 / 最大块 | 115 KB / 53 KB | **88.8 KB / 31.7 KB**（蓝牙没打开就少 26 KB：链接了蓝牙库，板卡包开机时就不再释放蓝牙控制器的内存） |
| 初始化后 | — | 31.5 KB / 23.5 KB（**初始化占约 50 KB**） |
| 主动扫描 5 秒 | — | 扫到 22 个设备；最低空闲 18.9 KB，最大块 13.8 KB |
| 释放（deinit）后 | — | 82.9 KB / **17.4 KB**（内存回来了，但碎片化，最大块从 31.7 KB 掉到 17.4 KB） |
| 被动扫描常开时跑 S5 | 20 轮全过 | 设备报「low memory, retry」，S5 两项失败 |

**结论**：默认配置下不能常开，也不能「用时开、用完关」（关掉后碎片化）。要做 BLE，至少需要：
1. **开关式**：设置里打开蓝牙后重启生效；关闭时开机就释放控制器内存，零开销（`btInUse()` 按开机前就能读到的标记返回）。
2. **调小 NimBLE 和控制器配置**：连接数、消息缓冲、扫描去重缓存、主机任务栈等，目标把初始化开销从约 50 KB 压到 20 KB 左右。
3. **开着就不关**：开机时在其他大块分配之前初始化，避免碎片化。
第二轮试验按 1–3 调完再测，数字达标后才进入实现。

### 第二轮试验（2026-11-08）：arena 与开关式

| 试验 | 结果 |
|:--|:--|
| 开关式：覆盖 `btInUse()` 返回 false，让板卡包开机释放控制器内存（蓝牙代码照常链接） | ready 空闲 90.4 KB、最大块 31.7 KB，**只比不释放多 1.5 KB**：链接蓝牙后少的 26 KB 不是「没释放控制器内存」造成的，原因还没查清 |
| arena：NimBLE 主机经 `nimble_platform_mem_*` 的分配走借来的一整块 | 想借 48 KB 被拒（ready 最大块只有 31.7 KB）；实际**经这组函数的分配只有约 10 KB**（块内 4 KB + 退回系统堆 3 次共 6.3 KB） |
| 初始化的其余开销 | **约 47 KB**：控制器（乐鑫预编译库内分配）、主机与控制器任务栈、事件队列，都不经过 NimBLE 的分配函数，arena 管不到 |
| 关蓝牙并还回整块后 | 最大块 31.7 → 21.5 KB，仍然碎片化 |
| 被动扫描常开 | 空闲约 25 KB，最低 23 KB |

**结论**：arena 只能管住约 20%，大头在控制器和任务栈；开关式无效。要让 BLE 可用，下一步只能动乐鑫库本身：重编自建 ESP-IDF 库，把蓝牙主机从 Bluedroid 换成 IDF 自带的 NimBLE、调小控制器配置（最大活动数、扫描去重缓存、连接数、任务栈），并查清链接后那 26 KB 的来源。工作量大（重编库约一小时起），BLE 先不进 0.6.1 的主线，等用户决定。

### 「链接蓝牙后少 26 KB」的来源（2026-11-08 查明）

对比正式固件与带 NimBLE 的试验固件（`xtensa-esp32s3-elf-size -A` + 链接 map）：

| 段 | 增量 | 来源 |
|:--|:--|:--|
| `.iram0.text` | +18.1 KB | 其中 **16.5 KB 是蓝牙控制器库 `libbtdm_app.a`**（`lld_adv`、`lld_con`、`lld_scan` 等链路层代码）被放进 IRAM。ESP32-S3 的 IRAM 与 DRAM 共用同一块 SRAM，堆随之变小（`.dram0.dummy` +17.9 KB 即同一块） |
| `.dram0.bss` + `.dram0.data` | +6.5 KB | 蓝牙的静态变量 |

合计约 24.5 KB，与实测 26 KB 相符（差值是对齐和堆管理开销）。所以开关式无效：它只释放控制器的数据内存，释放不了代码占的 IRAM。

**对策**：重编 ESP-IDF 库时打开 `CONFIG_BT_CTRL_RUN_IN_FLASH_ONLY`，把控制器代码放到 flash 里运行，预计收回约 16 KB；代价是写 flash（存文件）期间蓝牙时序可能受影响，需要实测。

## 七、flash 占用与优化（2026-11-08 分析 v0.6 发布构建）

flash 映射段合计约 3044 KB。大头：

| 项 | 大小 | 说明 |
|:--|:--|:--|
| 中文字体 efontCN 14 / 12 / 10 号 | 256 / 208 / 155 KB，**共 619 KB** | 含全部中日韩字形（两万多字）；12 号几乎所有页面在用，14、10 号只用于 SSH 页字号和少数标题 |
| LibSSH | 约 410 KB | 其中 Ed25519 预计算表 `ge25519_base_multiples_affine` 106 KB |
| Wi-Fi / lwip / wpa / phy | 约 365 KB | 系统，难压 |
| mbedtls | 约 147 KB | HTTPS 必需 |
| 自己的代码 | 约 940 KB | 分散，最大的 prog_runtime 45 KB |

**可做的优化（按收益）**：
1. **字体子集化**：三个字号只保留 GB2312（6763 个常用汉字）+ 标点符号 + ASCII，预计省约 400 KB；代价是生僻字显示成方框。用 efont 的 BDF 源按字表重新生成 u8g2 格式字体。
2. Ed25519 改用不带大预计算表的实现：省约 100 KB，SSH 签名变慢（每次连接只签一次）。
3. 小项：关 core dump（约 11 KB）等。

### 内存泄漏排查（已完成，见上表）

旧库上：开机 110 KB → 跑一轮 S6+S10 → 71 KB → 再跑 S10 → 61 KB → 再跑 S6 → 57 KB；最大连续块 43 → 13 KB。

1. 约 35 KB 是第一次运行时的一次性分配（懒加载缓存），之后不再大涨；
2. 每轮还会多出 3–6 KB 小块（慢泄漏）；
3. 碎片：最大连续块降到 13 KB 后，S10 有 7 项失败。

下一步：编一套打开 `HEAP_TRACING_STANDALONE` 的诊断库（重编几分钟），加接口开始 / 导出未释放的分配和调用地址，`addr2line` 定位到源码行。一次性缓存登记进 arena，泄漏修掉。
