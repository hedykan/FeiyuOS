# 0.7.4 计划：提示词精简与地址规范

> **状态：精简已进固件、上机验证通过（活文档）**。分支 `feat/v0.7.4`（从 `v0.7.3` 开出）。
> 来源：每次问模型，系统提示词约 7000 token，其中三分之二是 24 个扩展包的用法，不管这次用不用得到都整份发送；核心规矩和各包用法里还混着为单个用例写的特判（违反 `CLAUDE.md` 第二节）。
> 做法：先在本机的提示词实验（`tools/prompt_lab.py`，判第一步）和实验台（`tools/agent_lab.py`，整个任务跑到底）上做成变体、和现状并排对比，有数据再搬进固件，上机只做一次验证。

## 决定

| # | 决定 | 原因 |
|:--|:--|:--|
| P1 | 提示词 = 核心规矩 + 常驻包的用法 + 其余包的一行索引 + 收尾规矩 | 用法占三分之二，一次任务通常只用到一两个包 |
| P2 | 常驻还是按需由包自己声明：包有 `index()`（索引那一行的地址和关键动词）就按需，没有就常驻 | 新包自己决定，不在 agent 里写名单 |
| P3 | `discover`（capabilities）的 query 点名了按需的包，就返回它的简介和完整用法（`registry::package_help`） | 用现成的入口，不加新机制 |
| P4 | 写程序的做法并进 `prog://help`（「写程序的做法」一节） | 写或改程序前本来就读它；不写程序时不付这部分 token |
| P5 | `read prog://名字` 的结果头写明 `?grep=`、`?lines=` 和 `patch` | 改大程序时模型不读 `prog://help`，在用的那一刻告诉它 |
| P6 | 核心规矩和常驻用法只写协议和地址格式，删掉单个用例的特判（车库不译成 garage、厨房 ESP、NGX 指 nginx、XTheTMUX绘画、扣的差指 Codex……），改成通用约定 | `CLAUDE.md` 第二节；语音转写的错误由一条通用约定处理 |
| P7 | 工具定义只缩短说明文字，参数结构不变 | |

常驻（没有 `index()`）：memory、display、hardware、local、ssh、tmux、agents、policy、debug（三条全局流是调试契约，见 `CLAUDE.md` 第五节）。其余按需。

## 补回来的通用约定（v2 → v5，每条都对应一类失败）

- 用户对主机的叫法（中文英文都算）就是主机名，即使不在可见 profile 列表里也原样用，由设备校验，不为确认主机去 discover。
- 名称前的「配置」「主机」这类说明词不算名称，名称自带的「WiFi」这类字样保留。
- 家居设备的编号写进属性（light-1、relay-1），位置里只留地点；位置和设备名连成一段、大小写照原话。没说位置就澄清。
- 按需包的索引行写出关键动词和格式：WiFi 连接用 session(connect)，定时的时长格式，到点要做事用 trigger，读目录即列出，写或改程序前先读 `prog://help`。

### 搬进固件之后（上机）

- 实测首轮提示词：3560–3567 token（不含 discover 的用例），0.7.3 约 7000。
- 实验台：旧固件历次 69–72/74，新固件 68–72/74，在同一个波动范围；两边都没过的 `big_add_feature` 是用例本身难。
- `debug` 改为常驻：按需时 `dbg_last_output` 两遍都失败（模型去查 memory://recent-tasks 和 history，没想到 debug://stdout）。
- 索引行要写全这个包的主要动作。上机时又撞到三处：触发的新建、删除、清理（`trigger://new` 的内容、`/delete`、`clean`），扩展包的启用（只写了 install，模型去「安装」一个已在卡上的包），红外的 confirm、try、send。都补进索引后对应用例通过。

### 顺带修掉的

- 设备：`read pkg://catalog` 不带地址时会拉默认目录并把它存成当前目录，读一下就把目录换了，之后的安装找不到包。改为沿用上次用过的目录（`pkg_store::catalog`）。
- E2E：S11 的面板触发用完只停用不删，历次运行攒下 25 个，撞到 32 个的上限后 S10 建不了触发；改为删除。`non_utf8_output` 拿「空」字判断，模型说到「空格」就判失败；改为判断「是空的、空文件」这类说法。
- 工具：`prompt_lab.py` 照固件的新规则拼提示词（常驻包用法 + 索引）、回答 discover（点名按需包给用法），`\n` 转义还原成换行；`agent_lab.py` 读程序的结果头带提示；`check_usage.py` 也检查 `index()` 的文字。

## 开机（已改）

开机各步加了计时，就绪时记一条 `boot_ms`（`rom=… m5=… sd-mount=… mirror=… registry=… wifi=… ready=…`，毫秒）。上电到可用约 49 秒，拆开后：

| 步骤 | 原来 | 原因 | 改法 | 现在 |
|:--|:--|:--|:--|:--|
| 卡 → 板载闪存的镜像同步 | 32–35 秒 | 每次开机把 `/vat/things` 下约 140 个小文件整份重写到闪存（闪存写要擦块），不管有没有变 | `copy_file` 先比内容，一样就不写；程序日志（`/logs/`）不进镜像；卡 → 闪存的检查挪到开机 20 秒后，主循环每圈只列一个目录或比一个文件（运行中改的文件本来就当场同步，这一步只为了接住在电脑上改过的卡）；遍历时直接用目录项判断是不是目录，不再按路径再开一次 | 0.1 秒；后台检查约 8 秒，记 `mirror_check` |
| 注册扩展包 | 2.6 秒 | 为找出哪些程序是扩展包，读了全部约 70 个程序的文件头 | 程序索引每项记 `package`；只读标了包的；旧索引第一次开机时重建一次 | 0.04 秒 |
| 就绪前的 Wi-Fi 节点扫描 | 4.6 秒 | 阻塞扫描，`setup()` 返回前主循环不跑 | 异步扫描，`loop()` 里取结果记 `wifi_nodes` | 0 |
| 连 Wi-Fi | 4–5.5 秒 | | 不变 | |

上电到可用：约 49 秒 → 约 5 秒（刷机后第一次开机多一次索引重建，约 5 秒）。S0、S10、S12 通过。

## A10 代码模式（已做）

`write lua://run`，content 是一段 Lua：一次跑完，不保存。原来 `lua` 包只是原型（不在提示词里，结果是一串内存调试信息，脚本里要确认的调用一律拒绝）。

### 先量值不值

实验台加了 6 个多步用例（`multi_*`）。`fw` 与 `code` 必须分开运行：`prompt_lab.TEXTS` 是全局的，同一次运行里带草稿的变体会改掉其他变体的提示词和 discover 回答（踩过一次，那两轮数据作废；`agent_lab.py` 现在拒绝这样跑）。

| 用例 | 现在 | `lua` 只在索引里 | `lua` 用法常驻（v3） |
|:--|:--|:--|:--|
| 读 10 次加速度、每次隔 0.2 秒、取平均 | 10 轮 · 10.6 秒 · 45341 token | 没人用（模型不会去查） | **1 轮 · 3.1 秒 · 8317 token** |
| 连读三次电量、每次隔一秒 | 3 轮 · 3.6 秒 · 15694 token | 没人用 | **1 轮 · 2.5 秒 · 8240 token** |
| 灯、屏幕、提示音一起；磁盘内存负载；建三个目录；电量和姿态 | 1–2 轮 | 一样 | 一样（照样并行调用，不写脚本） |

- 互不相关的几件事，模型本来就一轮里并行调用完，代码模式省不了什么；省的是**循环、等待、按读数计算**：原来一轮读一次，「每隔 0.2 秒」实际隔的是模型思考的时间，或者往卡上存一个一次性的程序。
- 只放索引时模型从不去查：会改变做法的能力必须常驻。v2 的脚本里用 `vat.exec("sleep")` 等待、要多一轮：用法里直接写出 `vat.sleep`、返回表的常用字段后（v3）一轮完成。
- 代价：提示词每轮约多 315 token。
- 一同修的提示词：家居设备说了位置就直接调用、不先 discover（「解锁前门门锁」被问位置）；SSH 补回「有没有某个程序拿不准先 discover（capabilities，带主机），命令怎么用查 help」；红外索引列出电视动作名（开关都是 power）、第一次 content 写品牌、说没反应只 confirm no；timer 写明只提醒不做事，到点做事用 trigger；WiFi 写明用户的叫法就是网络名。

### 上机

- 时序：任务先改状态为 asking、后放问题，读的人可能看到 asking 却没有问题；按 Y 后脚本 50 ms 内才醒，读的人又看到旧的 asking。改为先放问题再改状态，交出答案的那一刻就把状态改回 running。
- 发版档 E2E 277/278（新增 `code_mode_asks`、`code_mode_rejected` 通过；S12 原来用 lua://run 验证联网要 @uses，改为存成程序再跑）；`heap_low_water` 51.7 KB；实验台 43 个用例 × 2：83/86，平均 4.0 轮、输入 27612 token（精简前 43167）；之后只改了 WiFi 索引行，意图用例全量 2 遍 208/208。

### 脚本里要确认的调用：原地问用户

Agent 的确认是「任务暂停 → 结束 → 按 Y 起新任务继续」，脚本的虚拟机不能跨任务暂停。新增通用的 `worker::ask()`：正在跑的任务把问题放进待确认（Agent 页 Y/N/A、状态里的 `pending`），任务状态为 `asking`，原地等；`ui::action()` 的 approve / reject / approve_all 在有任务等答案时直接交给它（返回该任务的编号），Agent 页在 worker 忙但有任务在问时也接受 Y/N/A。Esc 或 60 秒没回答算 N；等待时间不计入脚本的 150 秒。选「全部」放行本次脚本后面的确认。联网在程序里要 `@uses`，代码模式里也改为逐个问。

`programs::run_script()`：和程序共用运行、结果分段、三条全局流（记为 `lua://run`，来源「代码模式」）。

## A12 薄 Lua 外壳（这一版不做）

`CLAUDE.md` 第三节：扩展包可以选择性地给程序一个更短的写法（`pkg.foo()` 是某个地址的另一种写法）。统计实验台一轮里模型写的 78 份程序和脚本（7.7 万字）：

- `vat.xxx("地址"` 的写法一共 57 处、1802 字，占 2.3%：换成短写法最多省 1–2% 的输出，提示词却要多一份短写法的说明；
- 程序运行时因地址写错失败 2 次（来自专门测写错目标的用例）；「需要确认」49 次是在学 `@uses`，不是写错。

不省 token，也不减少错误：这一版不做。0.7.5 统一屏幕绘制后，程序会高频调用绘图（每帧几十次），那时短写法才有分量，作为 0.7.5 的设计输入。

## 地址规范化（已做）

盘点出 22 种协议头，动作位置、列表、设置、事件、本机硬件的写法各不相同（同一个包里 `pkg://install/名字` 和 `pkg://名字/enable` 并存；本机加速度和电量分在两处；LoRa 包还专门接受模型猜的写法）。规范写进 `docs/EXTENSION_PACKAGE_GUIDE.zh-CN.md` 第 5 章，是写扩展包的硬约束：

- 结构 `协议头://资源路径[/动作][?参数]`，动作只在最后一段、只用动作词表里的词（`help`、`run` 也可作名词在中间）；
- 按类别归属：读数 `sensor://`，本机部件和通道 `device://local/…`（LoRa、蓝牙、WiFi、红外并入，原来各自的协议头取消），偏好 `settings://`，事件 `<来源>://event/<名称>`；
- 可选硬件没接上时包的用法和索引不进提示词（`Package::present()`，LoRa、GPS 看硬件探测，位置服务看 Key），discover 查到时标「未接上，现在用不了」；
- 不留旧写法：调用旧地址不执行，直接失败并给出新写法（`address::retired()`，与开机改写同一张表；权限判断对旧地址放行到这一步，不先弹确认框）；卡上已保存的程序（含旧版和 v0.6.2 的 JSON 程序）、`approved.json`、`triggers.json`、面板应用开机时按同一张对照表改写一次（`address::rewrite`，版本记在 `/vat/things/.address`，事件 `address_migrated`）；仓库里的用例和文档用同一套规则的 `tools/readdress.py` 改写；
- `tools/check_addresses.py` 从指南的三张表读规则，检查各包的地址字面量和核心提示词，进 `make host-test`。

## 录音停在 0.4 秒（未解决，发版后发现）

现象：长按 Enter 录音，画面停在约 0.4 秒，松手后识别为空（「没听清」）。每次都正好录到 384 ms。

- 不是 0.7.4 引入的：把 v0.7.2、v0.7.3 的发布镜像写回去也能复现；E2E 不测真实麦克风，所以一直没发现。
- 卡在麦克风采样，不在写卡：坏的时候每次采样都等满 250 ms 超时（`fails` 多次、`capture_max=250ms`），写卡最长 27 ms。M5Unified 的 mic_task 拿不到 I2S 数据时每 100 ms 超时一次，`Mic.record()` 在两个缓冲槽都占满后一直等，界面就停住。
- 坏状态会跨过软重启和 USB 刷写（这两种都不给 ES8311 断电），之后又会自己恢复；正常时连录几十次都好。逐阶段跑 E2E 只在 S4（远程 Agent）之后短暂坏过一次（640 ms，下一次就好）。
- 排除：写卡、开机镜像检查、熄屏、提示音（扬声器播完就 `end()`）、语音识别上传、文字任务、录音开始删文件（`/vat/cache/ptt.pcm` 不进镜像，不写 flash）。
- 怀疑方向：ES8311（麦克风和扬声器共用 BCK/WS，ESP 复位时它不断电）的寄存器状态；待下次坏的时候彻底断电（关电池并拔 USB）看是否恢复来确认。
- 已加诊断：`ptt_recorded` 记下按住时长、采样失败次数、单次采样和写卡的最长耗时。
